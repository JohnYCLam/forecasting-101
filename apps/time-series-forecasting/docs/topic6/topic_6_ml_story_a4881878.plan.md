# Section 6 Traditional ML Recommendation Plan

## Narrative thesis
Section 5 showed that multivariate statistical models become fragile as predictors multiply, relationships drift, and linear structure is misspecified. Section 6 should answer: **Can we use many signals and nonlinear interactions without specifying one large system of equations?** Traditional ML can—but only after time is encoded as supervised features, and only with chronological validation.

The recurring case study should be a planning forecast (recommended: daily electricity load, 30 days ahead). Every subsection revisits the same pipeline and resolves the next problem, so the chapter does not become an algorithm catalogue.

Evidence from the supplied references must remain visible: [`Time_Series_Analysis_103.ipynb`](references/Time_Series_Analysis_103.ipynb) favors Random Forest in its reported CO₂ and bike results, whereas [`boost-vs-forest-ts`](references/boost-vs-forest-ts) is designed around load interactions where XGBoost can win. Treat this as evidence that **there is no universal tree winner**, not as a contradiction to hide.

## Recommended six-subsection arc

### 6.1 From a time series to a supervised-learning table
- **Question:** Why use ML after ETS, ARIMA, GARCH, and VAR/VECM?
- **Claim:** ML adds value when many lagged, calendar, and external signals interact nonlinearly; it does not understand time unless those signals are encoded safely.
- Introduce one-row-at-origin notation: features available at time `t` predict `y(t+h)`; show lag, shifted rolling, calendar, and known-future covariate groups.
- Begin with **seasonal naive + Ridge regression**, not Random Forest. Ridge is the interpretable bridge from the linear models already learned and reveals what changes when nonlinear trees arrive.
- **Graph behavior:** a selected-origin forecast above a feature-timeline strip; toggling feature groups updates the path and MAE. Explicitly mark the information cutoff so leakage is visually obvious.
- **Commentary beats:** Topic 5 limitation → table transformation → guided feature toggle → leakage warning → “algorithm choice comes next.”

### 6.2 One table, three ways to learn: Ridge, Random Forest, boosting
- **Question:** What does each model family do with the same information?
- **Claim:** Ridge learns one additive linear surface, Random Forest averages diverse trees to stabilize flexible rules, and gradient boosting sequentially corrects residual errors.
- Core methods: **Ridge/Elastic Net**, **Random Forest**, and one boosted-tree implementation (**XGBoost if available; otherwise sklearn HistGradientBoostingRegressor**). Mention Extra Trees, LightGBM, and CatBoost in a compact family guide; do not build separate demos for each. Keep kNN and SVR as optional “other common methods,” not main characters.
- Use a locked synthetic demand mechanism containing a nonlinear temperature threshold and weekday interaction; this establishes why trees can help without engineering a winner on real test data.
- **Graph behavior:** progressive residual view on the same dataset—Ridge misses the interaction, forest smooths it, boosting focuses successive trees on remaining errors. A complexity control changes depth/minimum leaf size and visibly shows underfit versus overfit.
- End by asking whether the mechanism survives honest real-world evaluation.

### 6.3 The forecast arena: fair comparison with Sections 1–5
- **Question:** Does nonlinear flexibility improve an actual forecast?
- **Claim:** ML should be chosen only when it beats strong earlier-topic baselines on untouched future windows with the same available information.
- Recommended real dataset: German daily electricity load from [`boost-vs-forest-ts/data/de_electricity_load_daily.csv`](references/boost-vs-forest-ts/data/de_electricity_load_daily.csv), because it supports lags, calendar effects, renewables, and price. Bike sharing can be a secondary robustness case, not a second full storyline.
- Compare **seasonal naive, ETS or SARIMAX, Ridge, Random Forest, and boosted trees** using the same horizons and expanding-window origins. Distinguish univariate and covariate-enabled baselines so ML does not win merely by receiving more information.
- Add feature-group ablation (history only → calendar → external drivers) and permutation importance. State that importance is predictive association, not causation.
- **Graph behavior:** origin selector controls the forecast path; aggregate view shows fold MAE distributions and win rate paired with gain size. Never rely on one showcase window or one average.
- Commentary explicitly reconciles the supplied references: RF can beat XGBoost on small/smooth series; boosting can win when repeated residual correction captures useful interactions; SARIMAX can remain competitive with the same regressors.

### 6.4 Multi-step forecasting: recursive or direct?
- **Question:** What exactly is the model asked to predict over a 30-day horizon?
- **Claim:** Recursive forecasts reuse their own errors, while direct horizon-aware forecasts avoid feedback but require more data and parameters.
- Reuse the direct multi-horizon design in [`boost-vs-forest-ts/src/models.py`](references/boost-vs-forest-ts/src/models.py), alongside a genuinely recursive implementation and a seasonal-naive path.
- **Graph behavior:** method toggle changes both forecast path and MAE-by-lead curve; animate or step through lead day so accumulated recursive error is visible. Show the training-target diagram before the score chart.
- This subsection carries the validation lesson: chronological train/validation/test, tuning only on validation origins, and no shuffled K-fold. A small leakage counterexample may be a warning inset, not the main demo.
- End with a decision rule: direct for fixed planning horizons and enough history; recursive for compact one-step systems when feedback is acceptable; neither is universally superior.

### 6.5 Where tree models fail: trend, extrapolation, and drift
- **Question:** Why can a highly accurate tree suddenly flatten or decay after deployment?
- **Claim:** Tree ensembles interpolate learned target regions; they do not naturally extrapolate a new level or trend, and stale feature relationships fail under regime change.
- Link back to Topic 2 differencing/detrending and Topic 5.7 stability monitoring. Compare level-target trees against differenced/detrended targets and a statistical trend baseline on a pre-specified trend-shift scenario.
- **Graph behavior:** extend the forecast beyond the training target range; the level-tree forecast plateaus while detrend-then-ML and a trend-capable baseline can move beyond it. A training-cutoff control shows when the failure begins.
- Include a deployment panel: rolling error, residual drift, and retraining checkpoints. Do not prescribe a universal threshold; describe sample-specific monitoring evidence.
- This is the main “when not to use ML” lesson: short clean univariate series, required structural interpretation, reliable intervals, or extrapolative trend may favor ETS/ARIMA/SARIMAX/VECM.

### 6.6 Advanced extension: probabilistic ML with quantiles and conformal calibration
- **Question:** Point forecasts rank models, but how uncertain is the decision?
- **Claim:** Quantile boosting can model asymmetric conditional ranges, while split conformal calibration uses held-out residuals to target empirical coverage without assuming Normal errors.
- This is the recommended VECM-like advanced topic because uncertainty is a real capability gap in ordinary RF/XGBoost point forecasts and creates a natural bridge to later deep-learning/foundation-model evaluation.
- Compare naive empirical intervals, statistical-model intervals, raw quantile-boosting intervals, and calibrated intervals on the same held-out origins.
- **Graph behavior:** confidence selector changes band width; coverage-versus-width chart shows that narrower is not automatically better. Highlight interval misses and coverage by calm versus high-load regimes.
- State scope carefully: finite-sample conformal coverage requires exchangeability-like stability; serial dependence and drift can break nominal behavior. Use rolling/block calibration as an advanced note, not an unconditional guarantee.
- End with a compact model-selection guide covering data size, nonlinear covariates, extrapolation, interpretability, interval needs, and compute.

## Commentary and visual contract
For every subsection, use 3–4 commentary tabs with one repeatable message each: **motivation → mechanism → guided evidence → decision/limitation**. Commentary must point to the active chart element and selected control; dataset cards contain facts only. All displayed metrics and claims come from generated JSON, with `n/a` rather than typed fallbacks.

Maintain continuity with a repeated question at each transition:
1. Can a feature table represent the history?
2. Which learner captures its structure?
3. Does it generalize against strong baselines?
4. Does the advantage survive the real forecast horizon?
5. What happens outside the learned regime?
6. Can uncertainty be calibrated for decisions?

## Scope recommendations
- **Main demos:** Ridge, Random Forest, and one gradient-boosted tree family.
- **Decision-guide mentions:** Elastic Net, Extra Trees, LightGBM, CatBoost, SVR, and kNN.
- **Do not add as full subsections:** exhaustive hyperparameter tuning, SHAP theory, every boosting library, or a leaderboard detached from forecast design.
- **Optional future deep dive:** global ML across many related series. It is valuable, but better saved as a bridge to Topics 8–11 than combined with the uncertainty subsection.

## Acceptance criteria
- A learner can explain why ML may help, how time becomes features, how RF differs from boosting, why chronological validation matters, how multi-step strategy changes errors, why trees fail to extrapolate, and when calibrated uncertainty is needed.
- The default view in every subsection visibly supports its stated claim.
- At least one honest case favors an earlier-topic model or Random Forest over boosting, preventing a predetermined “XGBoost wins” narrative.
- The final decision guide compares Sections 1–6 by evidence needs and operational constraints, not by a single global ranking.
